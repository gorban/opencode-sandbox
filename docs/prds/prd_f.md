# prd_f: Host tool dependencies, pinned and organised

[Index](README.md)

## Problem

New features add host tools (mkcert, certutil, maybe a DNS responder runtime). They should be pinned,
verified and kept in one place, not installed ad hoc.

## Reference

api-agent uses `mise.toml` (`[tool_config] locked = true`), `mise.lock` (checksums per platform), and
`lazy = true` so tools are fetched only when first used.

## Decision (2026-11-15)

**All host tools via mise** (user's choice): `mise.toml` + `mise.lock` in this repo, with mkcert from
aqua and certutil from conda's `nss` (a spike confirms it provides a working `certutil`; if not, choose
again).

## Spike result (branch `spike-f`, 2026-11-15)

Files: [`spikes/f/mise.toml`](spikes/f/mise.toml), [`spikes/f/mise.lock`](spikes/f/mise.lock) (both
real, usable as the starting point), [`spikes/f/probe.sh`](spikes/f/probe.sh) (re-runnable, removes its
scratch state, ends with `ALL CHECKS PASSED` only if every check ran and passed: 123 checks, 128 with
`PROBE_NEWER_MISE=2026.11.8`), [`spikes/f/lockcmp.py`](spikes/f/lockcmp.py) (compares two lock files by
content), [`spikes/f/probe-output.txt`](spikes/f/probe-output.txt) (one full run, with the newer-mise test). Host: Bazzite, devbox distrobox (glibc 2.43; host glibc 2.44), mise 2026.10.21 linux-x64.

### Hazards found (read these before writing code)

1. **`sql:/etc/pki/nssdb` is not what it looks like on this host.** `/etc/pki/nssdb/pkcs11.txt` loads
   `libnsssysinit.so`, which maps that db to the user's own db: **`~/.pki/nssdb`** or
   **`$XDG_DATA_HOME/pki/nssdb`** (`~/.local/share/pki/nssdb`); both exist on this host.
   `~/.pki/nssdb` wins when it exists (scratch probe with a marker CA in each: the listing of
   `sql:/etc/pki/nssdb` shows only the `~/.pki` marker, and the spike's accidental write landed there);
   the XDG db is the fallback used only when `~/.pki/nssdb` is missing (shown with an XDG-only scratch
   home, and by the reviewer's marker-cert test, which also used a scratch home without `.pki`). Listing
   `/etc/pki/nssdb` shows the user's CAs. Observed: `certutil -A` against a read-only copy of
   `/etc/pki/nssdb` wrote to `~/.pki/nssdb`; mkcert's `-A -d sql:/etc/pki/nssdb` exited 0 without
   changing `/etc/pki/nssdb`, and the CA appeared in the scratch `~/.pki/nssdb`, or in the scratch
   `$XDG_DATA_HOME/pki/nssdb` when only that existed. mkcert 1.4.4 has the path hard-coded, so
   `mkcert -install` always also goes there. In the spike a copy of that db, run with the real `HOME`,
   added a test CA to the **real** `~/.pki/nssdb` for about a minute. It was removed again with
   `certutil -D -n probe-ro` and the listing matches the one before, but the db files were rewritten
   (mtime 21:52). The probe now sets `HOME` and all four `XDG_*_HOME` variables to scratch, never points
   certutil at anything under `/etc/pki`, and never opens the real Flatpak dbs. The implementation's
   tests must do the same.
2. **mkcert escalates to `sudo`.** `execCertutil` retries with `sudo --prompt=Sudo password:` when
   certutil says `SEC_ERROR_READ_ONLY` (and `commandWithSudo` is used for the system store). A
   read-only NSS profile therefore produces a password prompt. This did not happen here, but is a
   reason not to call `mkcert -install`.
3. **mkcert leaf lifetime is fixed (2y3m)** and the leaf subject carries `user@host (Full Name)`. The
   30-day validity in [prd_e2](prd_e2.md) is not possible with mkcert (`-csr` removes the OU leak, not
   the lifetime). With the pinned OpenSSL, `openssl x509 -req -days 30` signs leaves
   with any lifetime and subject.
4. **Leaf names must stay inside the CA's constraint.** `localhost` (planned in prd_e2) breaks the
   chain; the apex `oc-sandbox.internal` does too with the leading-dot constraint. IP SANs are only
   limited if the CA carries IP subtrees, which it must always do (variant L or E). mkcert gives no
   error for any out-of-constraint name. Check names before issuing and run `openssl verify` after.
5. **A user's mise shims can shadow tools.** In the devbox, `openssl` resolved to a stale
   `~/.local/share/mise/shims/openssl` that fails under an isolated `MISE_DATA_DIR`
   (`openssl is not a valid shim`). Always run tools through `mise exec` (its PATH puts pinned tools
   first), never by bare name from the script's own PATH.
6. **`mise --cd DIR exec`** also changes the working directory to DIR, so pass absolute file paths.
7. **A probe that deletes must validate where.** The first probe accepted any `SCRATCH` that started with
   `<repo>/.scratch`, so `<repo>/.scratch/../.git` passed and the exit trap would have deleted it. The
   probe now requires a clean absolute path (no `..`, `.`, `//`, no symlink component) under
   `<repo>/.scratch`, creates a unique `mktemp -d` run directory, deletes only that directory (same
   device:inode, not a symlink, direct child of the base), and refuses hostile values before writing
   (section 0). The real implementation's tests should reuse `scratch_base_ok` and `remove_run_dir`.
8. **Silent success.** The first probe had no `pipefail` and several security claims rested on unchecked
   commands (for example an empty db after a failed `certutil -A` still printed the round trip as
   PASS). The probe now uses `set -u -o pipefail`, checks each operation and its resulting state
   (listed with `C,,` after `-A`, gone after `-D`), asserts the specific failure text for every
   intentional failure, counts setup failures as `UNEXPECTED`, and prints `ALL CHECKS PASSED` only if no
   check failed, no setup step failed and the number of checks that ran equals the expected number.
9. Real mise state: an unisolated mise call (the shell's mise hook on `cd`, or another session) refreshed
   `bin_paths` cache files for docker/lima in the real `~/.cache/mise` at 21:50 during the spike. None
   of the probes' own mise calls did this (they all export the `MISE_*_DIR` variables, and the final
   probe run's before/after fingerprint is clean).

## Conclusion

mise can provide everything: `aqua:FiloSottile/mkcert` 1.4.4, `conda:nss` 3.118 (a working
`certutil`, no missing libraries, no system packages), and `conda:openssl` 3.5.9, all locked with
checksums for linux-x64 and linux-arm64, installed in about a second, isolated from the real mise
directories. Lock enforcement works (a wrong checksum or an unlocked version fails the install).

Recommended setup:

- **Files**: `tools/mise.toml` and `tools/mise.lock` (use the spike's files; keep `[tool_config] locked
  = true`, `min_version`, `lockfile_platforms`, and the comment that records the mise version that
  generated the lock). Put them in a subdirectory, not the repo root, so a
  user who has `mise activate` in their shell does not get these tools in every shell in the repo. No
  `lazy`.
- **Data dir** (trusted path outside `~/opencode-sandbox`, validated like `$STATE`, and not a symlink
  into the sandbox): `~/.local/share/oc-sandbox/mise/{data,cache,state,config}`. Export
  `MISE_DATA_DIR`, `MISE_CACHE_DIR`, `MISE_STATE_DIR`, `MISE_CONFIG_DIR` (an empty dir), plus
  `MISE_CEILING_PATHS=<repo>`, `MISE_NO_ENV=1`, `MISE_NO_HOOKS=1`, `MISE_PARANOID=1`, only for these
  calls. **First unset every inherited `MISE_*` variable** (`MISE_GLOBAL_CONFIG_FILE` and
  `MISE_OVERRIDE_CONFIG_FILENAMES` can inject configs, and a plain `[tools]` file runs without trust).
  With `MISE_PARANOID=1`, record trust of `tools/mise.toml` explicitly (`mise trust`) in the isolated
  state dir once (tested: untrusted refused, trusted works). Never run
  `mise use -g` or touch `~/.config/mise`.
- **Calling**: `mise --cd "$TOOLS_DIR" exec -- mkcert|certutil|openssl ARGS` with absolute paths in
  ARGS. Not `mise which` (returns a wrapper script, fails for lazy tools). One call costs about
  20 ms.
- **Lock generator version**: the installer gives users the newest mise (2026.11.8 writes
  `lockfile_version = 4`; the committed lock is 3 from 2026.10.21), so a byte comparison of a
  regenerated lock is not reproducible. Options:
  - *Compare by content* (recommended, about 0.25 day): record the generator version in `mise.toml`
    (done), keep `min_version`, and have the CI/regeneration check use `lockcmp.py` (tools, versions,
    URLs, checksums, conda packages; tested: v3 and v4 from the same pins compare equal, a changed
    checksum is detected) and only warn when the running mise differs from the recorded one. Pros:
    works for every user and CI mise, and lets the lock move to a new format whenever someone
    regenerates it. Cons: ships a small comparison script; a new mise could add fields that matter
    (use `--strict` to see them).
  - *Pin the exact mise* (about 0.1 day): refuse to run `mise lock` or the check unless
    `mise --version` equals the recorded version. Pros: trivial, byte-for-byte. Cons: the documented
    installer installs the latest mise, so users and CI must install a specific version, and every
    mise upgrade needs a lock-format commit.
  Do not use a bare `diff` of lock files as a check.
- **Install**: when a TLS feature is first used, run `mise --cd "$TOOLS_DIR" install` (no-op in 30 ms
  when everything is present) and print `installing pinned tools (mkcert, nss, openssl) from the
  checksummed lock; about 80 MB` before it. Do it once per command, not per call. This gives lazy
  behaviour at feature level and avoids the shim problem.
- **Failure messages**: `mise` missing: `oc-sandbox: mise is required for local HTTPS (https://mise.jdx.dev); it is not installed automatically`
  (check with `command -v mise` before anything else; never auto-install). Install failure: print mise's
  own last lines, plus `check network access to github.com and conda.anaconda.org`; a checksum
  mismatch is fatal, never retried with `locked = false`.
- **Trust handling**: do not use `mkcert -install`/`-uninstall`. Use the pinned certutil directly on
  every existing db in the target list under "Where the browsers keep their NSS dbs" (including the
  Flatpak ones, which mkcert never sees), and **prove ownership before changing or removing anything**
  (reference implementation and checks in probe section 5b):
  1. *Fingerprint*: `openssl x509 -in ca.pem -noout -fingerprint -sha256` (DER SHA-256) is the identity
     of our CA. Use a nickname that includes it (`oc-sandbox-CA-<first 12 hex>`), but never rely on the
     nickname alone.
  2. *Before `-A`*: export whatever already has that nickname (`certutil -L -d sql:DB -n NICK -a`) and
     compare fingerprints. Same fingerprint: leave it unchanged and preserve any existing ownership record; never claim a pre-existing certificate merely because it matches. Anything else: **refuse** that
     db with a clear message and leave it as is. Otherwise `certutil -A -d sql:DB -t "C,," -n NICK -i
     ca.pem`, then re-read and check the stored fingerprint and the `C,,` trust.
  3. *Record* each db this installation changed in host state (`db`, `nickname`, `fingerprint`), under
     `~/.local/share/oc-sandbox/ca/` (trusted path), written after the verified add. Hold one exclusive lock in trusted state across validation, all NSS reads and writes, and every ownership-record update for both install and uninstall; do not unlink or replace the lock while it may be in use. The probe refuses database paths and nicknames containing control characters before touching a database, and validates the entire record file before any removal; malformed records are retained for recovery. A production implementation may instead use an unambiguous encoding that safely round-trips arbitrary POSIX paths. A crash between add and record can leave an unrecorded certificate; leave it untouched on uninstall and surface it for manual recovery.
  4. *Before `-D`*: for each recorded db only, read the cert currently under that nickname. Fingerprint
     equals the recorded one: `certutil -D -d sql:DB -n NICK`, then check it is gone. Different
     fingerprint (replaced by something else): print `left untouched` and do not delete. Absent: nothing
     to do. Never iterate over the target list for removal, and never delete by nickname alone.
  5. Skip any db that is missing or not writable and say so; never use `sudo` for NSS. Do not touch
     `/etc/pki/nssdb`. Run certutil with the real `HOME`/`XDG_*` only for these explicit paths.
- **CA and leaves**: create the CA with the pinned OpenSSL (use `openssl genpkey -algorithm EC
  -pkeyopt ec_paramgen_curve:P-256`, which writes PKCS#8 directly, so the key also works in a
  CAROOT). **IP identities are always constrained, independent of whether leaves use IP SANs**: a
  DNS-only constrained CA still signs a leaf for `192.0.2.7` (shown), so a leaked key could impersonate
  arbitrary IP endpoints. Two forms, both tested (final choice belongs to [prd_e1](prd_e1.md); never
  ship neither):
  - **Variant L** (loopback only): `nameConstraints=critical,permitted;DNS:.oc-sandbox.internal,permitted;IP:127.0.0.0/255.0.0.0,permitted;IP:::1/ffff:ffff:ffff:ffff:ffff:ffff:ffff:ffff`
    Needed if leaves carry `127.0.0.1`/`::1` SANs. Not `IP:::1/128`: OpenSSL 3.5 rejects it.
  - **Variant E** (no IPs at all, which spike e1 leans towards): `nameConstraints=critical,permitted;DNS:.oc-sandbox.internal,excluded;IP:0.0.0.0/0.0.0.0,excluded;IP:::/::`
    Leaves then carry only DNS names.
  Issue leaves either with mkcert (`CAROOT=... mkcert -ecdsa -cert-file ... -key-file ...`, names
  validated first; fixed 2y3m lifetime) or, preferably, with OpenSSL directly (any lifetime, clean
  subject). OpenSSL issuance requirements (tested in probe section 4b): generate keys under `umask 077`;
  sign with a **script-written** extensions file (`basicConstraints=critical,CA:FALSE`, `keyUsage`,
  `extendedKeyUsage=serverAuth`, the validated SANs only); **never** `-copy_extensions` from a CSR; use a
  fresh serial (`-CAcreateserial` with a serial file). With OpenSSL + certutil mkcert is **unused** and
  could be dropped from the pins; see the open decision below.
- **Tests**: a probe like `probe.sh` in `tests/` with a scratch `HOME` and scratch `XDG_*_HOME`, a
  validated unique scratch directory and a guarded delete (reuse `scratch_base_ok` and `remove_run_dir`),
  `set -u -o pipefail`, explicit checks of every operation and its resulting state, and an expected
  check count; assert the fingerprint of the real `~/.pki`, `~/.local/share/pki`, `~/.local/share/mkcert` and every
  `~/.var/app/*/{config,data}` NSS file is unchanged.

### Risks and unknowns

- arm64 entries are generated but never run.
- Firefox's profile db was only exercised as a scratch profile created with `certutil -N`; the real
  Flatpak Firefox and Chrome (does the sandbox read the db we edit, is a CA added from the host
  honoured, Firefox version and enterprise-roots) are untested, as is the Edge/Chromium/ungoogled
  first-run db creation. Chrome's NSS validation was tested through `certutil -V`, not Chrome itself.
- **Supply chain**: mkcert 1.4.4 publishes no checksums or signatures, so the lock's checksum is
  trust-on-first-use of the GitHub release asset (via the aqua registry / API). The conda checksums
  come from the conda-forge channel index over HTTPS; no package signature is verified. The lock
  prevents later substitution, not a bad first lock. Review lock diffs.
- `conda:nss` links the host glibc; a much older host libc could break it (here 2.43/2.44). The
  lock pins exact conda builds, but a conda-forge package removed upstream would break a fresh install
  (the checksummed cache only helps after the first install).
- Locking needs the GitHub API for mkcert asset ids; unauthenticated rate limits can hit
  `mise lock` (not `mise install`).
- mise itself is not pinned: `min_version` guards the minimum only; see "Lock generator version" for the
  lock-format consequence (tested with mise 2026.11.8 only).
- In this spike NSS's enforcement of IP name constraints was tested for variant E only (DNS leaf valid,
  IP leaf invalid). The separate [E1 host-browser subset](prd_e1.md#host-browser-subset-2026-11-16)
  later tested Firefox and Chrome with E's IPv4 exclusion; it did not cover the full IP matrix.
- This spike tested the leading-dot form with OpenSSL and NSS. The separate E1 host-browser subset
  tested an allowed subdomain and a disallowed DNS name under E; browser behavior for the bare name
  and the full set of constraint variants remains untested on the host.
